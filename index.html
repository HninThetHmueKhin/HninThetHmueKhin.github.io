Moving a SOAP service to REST: what I check firstLessons from helping migrate 70+ services at KBZ Bank.

At KBZ Bank I was part of the team that moved more than 70 Oracle SOAP services to REST APIs. Changing the technology is the easy part. These are the things I’d check before writing any new endpoint.

  • Who calls it, and what do they really use? A WSDL can describe dozens of fields that nobody reads. Talk to the consumers before you copy the contract one to one.
  • Keep the behaviour, change the shape. First make the REST version do exactly what the SOAP one did. Improvements can come later. Where you can, run both side by side and compare the responses.
  • Decide how errors look, early. SOAP has faults. REST has HTTP status codes and a response body. Pick one consistent error format for every endpoint so consumers don’t have to guess.
  • Validate on purpose. SOAP stacks often check the schema for you. In ASP.NET Core you add validation yourself, so don’t assume it’s there.
  • Test with awkward data. Nulls, long strings, dates and decimal amounts cause more trouble than the happy path, especially around payments.
  • Document it. A Swagger page saves you from answering the same question for every team.

The biggest lesson was that the contract matters more than the technology. If consumers can switch over without surprises, the migration worked.

Tracing a production bug through three layersHow I work through a data problem I can’t watch happen.

When something is wrong in production, I try not to guess. This order works for me most of the time.

  1. Get the exact example. A real record, request or order number beats “it sometimes fails”.
  2. Look at the data first. What is actually stored, and what changed it?
  3. Check the boundary. Problems often sit between two systems, so compare what one side sent with what the other received.
  4. Read the logs around that moment. A correlation ID that follows a request through every layer makes this much faster, so add one if you don’t have it.
  5. Only then read the code, once you know which layer to look in.
  6. Fix it, add a test that would have caught it, and tell the people who were affected.

I work across the application, integration and database layers, so I like having a way to narrow things down quickly. It also keeps the conversation with the business calm, because I can say what I’ve already ruled out.

The Repository Pattern in ASP.NET Core: useful, but keep it smallWhat I learned using it on a bank customer system.

I used the Repository Pattern on the customer CMS at KBZ Bank. It helped, and I’d use it again, but I’d be more careful about how much of it I build.

What it gives you. Data access sits in one place, your business code doesn’t depend on how the data is stored, and you can swap in a fake repository for unit tests.

What to watch for. Entity Framework Core’s DbContext already behaves like a repository and a unit of work. If your repository only forwards every call to it, you’ve added a layer for nothing.

  • Keep interfaces small and specific to what the code needs, such as “get customer by ID” or “search customers”.
  • Be wary of one generic repository for every table. It tends to leak query details and gets awkward the moment one case is different.
  • Don’t return IQueryable from a repository unless you really want callers building queries.
  • Register repositories with a scoped lifetime in dependency injection, so they share the same DbContext within a request.

For a small app, plain DbContext may be enough. Reach for repositories when you need to test business rules in isolation, or when data comes from more than one place.

Running an ASP.NET Core app in Docker on Linux: the basicsWhat I’d tell myself before the first deployment.

The customer CMS I built at KBZ Bank ran in Docker on a Linux server. If you’re used to Windows and IIS, the move to containers is mostly easy, but a few habits save a lot of time.

  • Use a multi-stage Dockerfile. Build with the .NET SDK image and copy the published output into the smaller ASP.NET runtime image. You ship less, and the build tools stay out of production.
  • Know which port you’re on. Recent .NET images run as a non-root user and listen on port 8080 by default, not 80. Map it explicitly when you run the container.
  • Keep secrets out of the image. Connection strings and keys belong in environment variables or a secret store, not in settings files baked into the image.
  • Log to the console. Write logs to standard output and let the platform collect them, instead of writing files inside the container.
  • Add a health check endpoint. It tells Docker or your load balancer when the app is actually ready, not just started.
  • Mind the reverse proxy. Behind nginx or a load balancer, configure forwarded headers so the app sees the real scheme and client address.
  • Use a .dockerignore file and pin image versions. Builds stay fast and repeatable.

None of this is clever. It’s a checklist, and it’s worth running through every time you containerise something.

Making EDI and API integrations less painfulWhat I learned building integrations for enterprise customers.

At Poh Tiong Choon I built REST APIs and EDI integrations for enterprise customers. Integrations rarely fail because of the code. They fail because two companies understood a message differently. This is what helps.

  • Agree the contract in writing, with real samples. Get example files or messages from the other side early, and build against them.
  • Store the raw message. If you keep exactly what you received, you can replay it after a fix and show what was sent.
  • Make processing safe to repeat. Retries and duplicate messages will happen. Design it so receiving the same message twice doesn’t create a second order.
  • Reject clearly. When a message is wrong, say which field and why, so the other team can fix it without a call.
  • Watch for failures. A failed integration that nobody notices is worse than one that fails loudly. Add alerts and a simple way to see what’s stuck.
  • Treat mapping as code. Keep field mappings in one place, test them, and review changes like any other change.

A good integration is boring. The other team sends data, it arrives, and nobody has to think about it.
